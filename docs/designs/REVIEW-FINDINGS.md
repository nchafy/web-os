# Verified review findings

Findings raised by 11 critics against four candidate architectures, each then put to an
adversarial verifier whose default was `refuted = true`. 24 of 44 survived; 20 were refuted.

Severity is the verifier's corrected severity, not the critic's claim. "Applies to all designs"
marks a finding the verifier judged to be a property of any design in this space, not of the one
it was raised against — those are the ones that became constraints.

## 1. A process can only ever be parked on one wait at a time and a winid is not an fd, so a process with two windows, or with one window plus a pipe/pty, has no way to be woken by both — which breaks acceptance criterion 2 outright and silently freezes the terminal.

- Severity: **major** (confidence high)
- Raised against: `fidelity-first`
- Address: THE DESIGN -> process_model ("Events return through win_poll(winid, timeout)") and runtime (the 46-call v1 list: `poll` appears in the fd group, `win_poll` in the window group, with no winid->fd mapping anywhere). Held against /Users/chafyni/claude/web-os/docs/research/gap-03.md line 25 (poll is `nfds x {i32 fd,u16 events,u16 revents}`) and line 36 (`win_poll(winid,timeout)`), and against POSIX poll, which is the primitive that exists precisely so one thread can wait on several sources: https://pubs.opengroup.org/onlinepubs/9699919799/functions/poll.html

**Failure scenario.** The ABI gives each process exactly one futex word (SEQ) and one outstanding call; `poll(nfds, {i32 fd,u16 events,u16 revents}, timeout)` is defined over FDs only, while window events arrive through a separate `win_poll(winid, timeout)` that takes a single winid. (a) TWO WINDOWS: Explorer opens /home/u in winA and /usr in winB and parks in win_poll(winA, 16ms). Clicks in winB do nothing until winA happens to produce an event or the timeout expires, so winB runs at the poll cadence and its scrollbar drag drops every intermediate sample. Acceptance criterion 2 says two windows must be expressible; as specified, the second window is only reachable by round-robin polling. (b) TERMINAL (M8, day ~125): the terminal process holds a WIN_CANVAS surface and a pty master fd. Park in read(masterfd) and keystrokes pile up unread in the kernel's window queue, so typing does nothing while `cat bigfile` runs; park in win_poll(winid) and the master is never drained, so the pty buffer fills, the child blocks, and the screen stops updating until the user presses a key. The only escape is a busy-poll loop of win_poll(timeout=8ms) + O_NONBLOCK read, i.e. 2 syscalls x 120 Hz per windowed process — which contradicts the design's own 'signals, broadcasts and thumbnail pushes are O(interested), never O(N)' rule the moment more than a handful of windows exist. (c) The harness cannot see any of this: M8's `yes | head -3` and Ctrl-C checks never type while output is flowing, and M5/M7 never drive two windows of one process, so every stated check passes on a broken terminal.

**Fix.** Make a window a file description: `win_create` returns an fd (and /proc/<pid>/win/<winid> is openable), window events become the fd's readable set, and `poll()` is the single wait primitive for fds, pipes, ptys, waitpid-via-pidfd and windows alike. This also lets win_poll be deleted from the call list. Move it into M2's ABI, not M7/M8 — libc.mjs and every app written against win_poll change otherwise. Add an M8 check that types into the terminal WHILE `yes` is producing output, and an M5 check that drives two windows of one process alternately.

**Verifier.** CORE MECHANISM: CONFIRMED, at the cited address.

- /Users/chafyni/claude/web-os/designs/fidelity-first.md:362 — `win_poll(winid, timeout_ms)`, one winid, no set, no wildcard, no winid 0/-1 "any window" form.
- :415 and :419 — the v1 table puts `poll` in the fd group and `win_poll` in the window group. I grepped the whole file for `pollfd|epoll|select(|window.*fd`: there is no winid-to-fd mapping anywhere.
- /Users/chafyni/claude/web-os/docs/research/gap-03.md — `poll(nfds, byteregion = nfds x {i32 fd,u16 events,u16 revents}, timeout_ms)` and `win_poll(winid,timeout)`; control words give one futex word (`i32[0]=SEQ`, "the only futex word") and §4 states a process "blocks on exactly one futex word". No clone, no pthread, no per-thread SAB, so a process is single-threaded and cannot park twice.
- POSIX poll (URL above, fetched): every input is a file descriptor; behaviour on anything else is unspecified. So `poll` cannot be stretched to cover a winid.
- The two-source process is not hypothetical in this design: fidelity-first.md:470-472 says the shell process "gets a pty from `pty_open`, a `WIN_CANVAS` surface, and a terminal grid renderer" — one process holding a master fd and a window. :725 (`/proc/<pid>/win/<winid>/...`) confirms multiple windows per process are intended.

So the expressiveness gap is real: there is no unified wait, and the only way to service a window plus an fd is a bounded-timeout loop over two calls. The proposed fix is sound and is not a wish: the sibling design minimal-kernel.md:55,129 deletes the whole `win_*` group in favour of `/dev/wm` as a file, so window events land on an fd and `poll()` covers them. Not universal context — it is a choice this design made, shared with hybrid-guest and wasi-userland, and avoided by minimal-kernel.

WHAT IS WRONG IN THE FINDING (why it is major, not fatal):

1. "Silently freezes" is refuted. fidelity-first.md:629-634 defines Not Responding as a two-threshold machine on the kernel's sequence-numbered heartbeat: caption greys at 1,000 ms, End Process dialog at 5,000 ms. A window whose events go unconsumed is exactly what that detector is for. And `win_poll` carries a timeout, so an unbounded park is the app's choice, not something the ABI forces.

2. "Its scrollbar drag drops every intermediate sample" is refuted. :362 says win_poll returns "packed event records" — plural, kernel-queued. A poll at 16 ms cadence delivers every queued move sample in one batch. The cost is latency bounded by the timeout, not sample loss.

3. Scenario (b) is backwards on its own facts. "Typing does nothing while `cat bigfile` runs" is the one case that works: output flowing means `read(master)` returns constantly, so the loop gets frequent chances to drain the window queue. The genuinely bad case — parked in `read(master)` with no output, at idle, keys dead indefinitely — is the one the critic did not name.

4. The O(N) escalation misreads the rule it cites. fidelity-first.md:393-396 and gap-04.md:140 are about kernel-initiated fan-out to all processes at 378 us per worker round trip. A process-initiated syscall is 14-16 us, ~550 per 8.3 ms frame. Two calls per 8 ms per windowed process is ~20 syscalls/frame at ten windowed processes, under 4% of frame syscall capacity. Wasteful and power-hungry, not a budget breach.

5. "Breaks acceptance criterion 2 outright" overstates. Two windows per process are expressible — `win_create` twice, `/proc/<pid>/win/<winid>`. What is missing is an efficient unified wait.

6. Part (c) is addressed to the wrong document. `yes | head -3` is hybrid-guest.md:396,673; the Ctrl-C / `sleep 30` check is minimal-kernel.md:496. Neither string appears in fidelity-first.md, whose milestone table (:877-890) has no check column at all. The weaker true statement — this design states no check that drives two windows of one process or types while output flows — holds only because it specifies no per-milestone checks to begin with.

VERDICT: a real ABI defect in a public interface, cheap to fix at M2 and expensive after M7/M8 as the critic says, with a working bounded-latency workaround and a detector that makes the degradation visible. That is major. Fatal is reserved for a design that cannot work.

Sources read: the four local files above (design + gap-03 + gap-04 + the sibling designs) and the POSIX poll page. gap-04.md contains nothing on window event delivery beyond the O(N) line; the gap is not pre-handled there.

Evidence: https://pubs.opengroup.org/onlinepubs/9699919799/functions/poll.html

## 2. There is no way to drag a file from one app to another, and no way to copy anything that is not raw bytes of one unnamed type — the shell's two most-used verbs have no slot anywhere in the ABI, the widget vocabulary, or the compositor.

- Severity: **major** (confidence high)  —  **applies to every design**
- Raised against: `fidelity-first`
- Address: THE DESIGN, `runtime` syscall list (window group: win_create win_set win_surface win_thumb win_poll win_destroy notify clipboard_read clipboard_write) and `shell_and_wm` widget vocabulary; the inherited ABI is /Users/chafyni/claude/web-os/docs/research/gap-03.md line 36 (`clipboard_read`/`clipboard_write`→bytes/0, no format argument) — neither file mentions drag-and-drop at all, and `what_it_gives_up` does not list it. Windows contract: https://learn.microsoft.com/en-us/windows/win32/com/drag-and-drop (IDataObject/IDropTarget) and https://learn.microsoft.com/en-us/windows/win32/shell/clipboard (CF_HDROP is how the shell moves files).

**Failure scenario.** User opens Explorer on /home/u/Pictures and Notepad side by side, and drags photo.png onto the Notepad client area. Explorer is a worker whose only outbound window calls are win_set(WIDGET_TREE)/win_surface/win_thumb, and its only inbound events come from win_poll on its OWN winid; the 18-type widget vocabulary (window panel groupbox label button checkbox radio textbox combobox listview treeview menubar toolbar statusbar scrollpane tabs progress splitter) has no drag-source or drop-target node and no drop event. The pointer-down on a listview row is delivered to Explorer as a click, the drag does nothing, and the cursor never changes. Same for copy: user selects photo.png in Explorer, hits Ctrl+C, then Ctrl+V in Paint — clipboard_write takes `bytes` with no format tag (gap-03 host group: `clipboard_read`/`clipboard_write`→bytes/0), so there is nowhere to put CF_HDROP (a path list) or CF_BITMAP, and the receiver cannot tell a pasted PNG from a pasted UTF-8 string. Also unreachable: drag a file to the desktop, drag a selection between two Explorer windows, drag a .txt onto Notepad's taskbar button. Windows 7 Explorer without drag-and-drop is a file list, and this is the single loudest 'website with a taskbar' tell in the design.

**Fix.** Add a kernel-owned typed data object to the ABI, not a byte blob: dataobj_create(formats[])->did, dataobj_set(did,format,bytes), dataobj_get(did,format), with a registerable format table seeded with TEXT/UNICODETEXT/HDROP/BITMAP. clipboard_read/write take a format. Add drag_begin(winid,did,allowed_effects) plus DRAG_ENTER/DRAG_OVER/DRAG_LEAVE/DROP events on win_poll with a drop-effect reply, and drag-source/drop-target attributes on the widget node types plus a WIN_CANVAS drop rect. The payload must be kernel-owned so a drag survives the source process entering DYING mid-drag. Add a milestone check: drag a file from the Explorer process to the Notepad process and assert the bytes arrive in the target with format HDROP, plus a negative control that dropping on a non-target leaves the file where it was.

**Verifier.** I tried to refute this and could not refute its existence, only its severity.

MECHANISM — REAL, addresses accurate. /Users/chafyni/claude/web-os/designs/fidelity-first.md line 419 lists the window group as exactly the nine calls quoted; §4.2 (lines 346-366) defines win_create/win_set/win_surface/win_thumb/win_poll/win_destroy with win_set props limited to TITLE ICON RECT STATE WIDGET_TREE PROGRESS OVERLAY_ICON THUMB_TOOLBAR; §5.7 line 616 lists the 18-node vocabulary verbatim as quoted, with no drag-source or drop-target node. The only win_poll event types named anywhere in the design are WIN_THUMB_WANTED/WIN_THUMB_IDLE (line 570). `grep -ril "dataobj|HDROP|DRAG_ENTER|drag_begin"` over the whole project returns nothing; every hit for "drag" in the design is caption drag, Aero Snap thresholds, or check.py's drag() helper. gap-03.md line 36 reads `clipboard_read`/`clipboard_write`→bytes/0 ACCES NOTSUP, with no format argument — exactly as cited. gap-03 and gap-04 never mention drag-and-drop (check 3: not already handled). Both external citations resolve and support the Windows contract: the shell clipboard page states "Shell data is always contained in a data object that uses a FORMATETC structure" with cfFormat the format tag, and CF_HDROP as the predefined format carrying a double-NUL path list; the COM page confirms IDropSource/IDropTarget/DoDragDrop.

One sub-claim is wrong: `what_it_gives_up` does not exist in any file in the project (grep is empty), so "what_it_gives_up does not list it" cites a field that isn't there. Non-load-bearing.

SCENARIO — follows, but narrower than claimed. Cross-process drag (Explorer → Notepad, Explorer → Explorer) and typed paste are genuinely unreachable: no event, no node attribute, no format tag. But two of the three "also unreachable" cases are not. Because §4.2 gives the shell ALL DOM and every window's widget tree as data, a drag from an Explorer listview row to the desktop or to a taskbar button lands on shell-owned DOM with a shell-owned source node; the shell can hit-test, render the drag image, and perform the VFS rename itself under the user's credential (§6, the credential change) with zero ABI additions. The critic also asserts "the cursor never changes," which presumes the shell declines feedback it is structurally able to render. The scenario also assumes Explorer and Paint exist; the design names only /usr/bin/notepad (line 540) and folds apps into an unitemised 13,300 LoC, so the apps are a fair extrapolation of intent rather than a spec reading.

SEVERITY — fatal is wrong; major. Against this design's own stated fatal bar (§0 and §12: if url() inside backdrop-filter fails, "the design is dead as written" — kill criteria 1 and 2), a missing verb in a call table that explicitly ships 46 of gap-03's 68 and lists 22 deferred calls, with a vocabulary labelled "versioned," is an incompleteness, not a kill. The fix is purely additive and cheaper here than in any other architecture surveyed: the gesture, drag image, hit-test and target highlight are all shell-internal, so there is no HTML5 dataTransfer and no cross-agent-cluster hop — which matters, because the measured facts say a SAB sent across agent clusters arrives as messageerror, so a per-origin design would pay far more for the same feature. The critic's own "payload must be kernel-owned so a drag survives DYING" is already this design's standing invariant (gap-03 §4: all releasable state "lives in the kernel, never in the worker"), so the fix aligns with the architecture instead of fighting it. Nothing measured is contradicted and no milestone is invalidated; the work lands inside M7 (widget protocol, 22 d / 3,000 LoC).

It is not minor, for one reason the drag half obscures: the clipboard gap is an ABI defect, not a missing feature. `clipboard_write(bytes)` with no format tag leaves a receiver structurally unable to distinguish a pasted PNG from pasted UTF-8, and the repair changes an inherited syscall signature plus a vocabulary the design declares closed — breaking processes already written against v1. That earns major.

CHECK 5 — shared, not universal. No candidate design has it: hybrid-guest line 359 and wasi-userland line 445 carry the same bare clipboard_read/write, and minimal-kernel replaces win_*/clipboard_* with /dev/wm (lines 55, 129) and likewise never mentions drag. The gap is inherited from gap-03's ABI table, so it applies to all four, but it is not a property of every possible design — a design could have specified it. Note that minimal-kernel's filesystem-as-WM would absorb a drag protocol as files with no new syscalls, so its severity there would be lower still.

Evidence: https://learn.microsoft.com/en-us/windows/win32/shell/clipboard

## 3. The "frame-only glass is 10.1x cheaper" headroom and the whole area governor are computed on the frame RING area, but backdrop-filter is filtered over the element's BORDER BOX, so a frame with an opaque client-area child still pays the full window area — the governor under-counts by ~10x and never fires.

- Severity: **major** (confidence high)
- Raised against: `fidelity-first`
- Address: design.thesis ("frame-only glass is 10.1x cheaper at 640x440 and moves the wall from ~51 windows to ~519") and design.shell_and_wm "Area governor with hysteresis: GLASS_OFF_AT 45e6 device px", plus milestone 4 proof (e). The spec text the design itself quotes contradicts it: /Users/chafyni/claude/web-os/docs/research/gap-04.md:115 — "backdrop-filter filters the element's Backdrop Root Image 'clipped to the element's border box', which is why total cost scales as the sum of each glass element's own area" — and https://drafts.fxtf.org/filter-effects-2/#BackdropFilterProperty / https://developer.mozilla.org/en-US/docs/Web/CSS/backdrop-filter. Note 281600/27888 = 10.097, so the 10.1x figure is exactly the ring/box ratio, confirming the accounting.

**Failure scenario.** On the measurement machine (dpr 2), open 5 maximized 1280x720-CSS glass windows and drag one. Real blurred cost is 5 x 3,686,400 CSS px x 4 = 73.7 M device px, past the measured 58-63 M wall, so the drag runs at ~62 fps or worse. The governor, summing rings (caption 30 + 6px borders => 109,008 CSS px each), computes 2.2 M device px — 4.8% of GLASS_OFF_AT 45e6 — and leaves every window on glass. Milestone 4 check (e) cannot catch this: it "raise[s] glass windows until summed glass device area passes 45e6", which under ring accounting needs ~403 windows of 640x440 (45e6 / (27,888 x 4)); the harness will never get there, so the author will lower the threshold or declare the check green. The governor is then validated against its own wrong area model while frame rate collapses at ~51 windows / ~4 maximized ones.

**Fix.** Either decompose the frame into four separately backdrop-filtered strips (caption + left/right/bottom edges) so the filtered border boxes really are the ring, or keep one glass element and re-derive the budget at full window area. Both change the numbers: per /Users/chafyni/claude/web-os/docs/research/05-platform-primitives.md:183-187 each backdrop-filtered element costs its own offscreen buffer and filter pass, so strips mean 4 render surfaces per window, and the governor must sum each glass element's border box, measured, not the ring. The M4 (e) check must assert frame rate under the governor's own OFF threshold, not just the mode flip.

**Verifier.** SURVIVES, but downgraded fatal -> major. The mechanism is real; the failure scenario's arithmetic is wrong by 4x; one quoted address is fabricated.

1. MECHANISM: CONFIRMED. fidelity-first.md:118-121 specifies exactly ONE .glass node per .frame, a sibling of .caption and .client, and never states its geometry. The area model at :270 is a RING - glass_area = w*caption + 2*inset*(h-caption) + w*inset - three disjoint regions. No single element's border box can be a ring. The border-box clipping rule is transcribed twice in this project's own research: research/gap-04.md:115 and research/05-platform-primitives.md:184-187 ("Each Aero window with backdrop-filter costs one offscreen buffer the size of its border box plus a filter pass... Twenty overlapping windows is twenty render surfaces, not one"). So the governor at :288-298, fed sumGlassDeviceArea from the ring formula, under-counts by 10.07x at 640x440 and 16.95x at 1280x720. Caveat: I read the spec as transcribed locally at those two addresses (both cite drafts.csswg.org/filter-effects-2/#BackdropFilterProperty; the critic's drafts.fxtf.org host differs from what the research cites). I did not fetch the live spec.

2. SCENARIO: DOES NOT REPRODUCE AS WRITTEN. The design's table at :274-277 is already in DEVICE px, not CSS px: 640*440 = 281,600 CSS px^2 * dpr^2 4 = 1,126,400 = the stated "1.126 M", and 58e6/1.126e6 = 51.5, which is exactly how the design reproduces gap-04's "~51 windows of 640x440". The critic took the 1280x720 entry 3,686,400 - already device px (1280*720*4) - called it CSS px and multiplied by 4 again. Real cost of 5 maximized 1280x720 glass windows is 5 * 3.686 M = 18.4 M device px, well under the measured 58 M wall, so that drag holds 120 fps. There is no "~62 fps or worse" and no collapse at "~4 maximized" windows; the true crossing is 15.7 at 1280x720, and gap-04 measured ~13 full-screen. The headline repro must be rebuilt.

3. THE DEFECT AT CORRECTED NUMBERS: STILL REAL. At the genuine wall of 51.5 windows of 640x440, ring accounting sums 5.76 M device px = 12.8% of GLASS_OFF_AT 45e6, so the governor demonstrably never fires before frame rate halves. The load-bearing casualties are thesis item 2 at :22-26 ("the measured budget does not bind") and :95 ("519 windows of headroom, against a process table capped at 512"): under border-box accounting frame-only glass buys nothing and headroom is ~51, not 519.

4. FABRICATED ADDRESS. The critic quotes M4 proof (e) verbatim as "raise[s] glass windows until summed glass device area passes 45e6". grep over the entire project (18 files) returns zero hits for "summed glass device area", "45e6" outside :291/:294, or any "(e)" proof list. :901 says only "Per-milestone proofs and negative controls are in the schema", and no schema file exists in /Users/chafyni/claude/web-os. The reasoning that the governor check becomes un-triggerable and gets weakened is sound in kind - :872 does require "flat above 45 M, glass below 36 M" - but the quotation is invented and per adversarial-review the address must be sent back.

5. NOT FATAL, AND NOT UNIVERSAL. Severity is major: a safety mechanism that provably never fires plus two wrong thesis numbers, with a local fix that leaves the architecture intact. Tier 1 DOM glass survives either way - the design still runs ~51 windows / ~13 full-screen, which the governor handles once its area function is corrected. The critic also ignores a charitable reading: the CSS at :216 uses the descendant selector ".frame .glass", which permits several glass children, and under a four-strip reading the ring formula at :270 is already correct and only the 4-surfaces-per-window cost from 05-platform-primitives.md:184-187 is unaccounted. Either way a gap must be closed, so the finding stands - but it is "glass geometry unspecified and the governor's area model unvalidated", not "the governor is 10x wrong and the design is dead". Design-specific, not context: hybrid-guest.md:910 states the border-box rule and wasi-userland.md:633 has the governor summing border-box area, while fidelity-first.md contains no occurrence of "border box" at all.

Minor nit: the critic's ring figure 27,888 should be 27,960 CSS px^2 (27,960*4 = 111,840 = the design's stated 0.112 M); immaterial to the ratio.

Evidence: https://drafts.csswg.org/filter-effects-2/#BackdropFilterProperty

## 4. Linux 2.6.34 — the exact kernel in the measured v86 Buildroot image — has no 9P2000.L operations at all, so the entire .L server in M0/M3 (Tlopen, Tgetattr, Tsetattr, Treaddir, Treadlink) is a dialect the guest never speaks, and mounting with version=9p2000.L is strictly *less* capable than 9p2000.u.

- Severity: **major** (confidence high)
- Raised against: `hybrid-guest`
- Address: THE DESIGN → milestones[0].deliverable (the 9-message .L list and the `version=9p2000.L` mount) and milestones[3] ("the full ~24-message 9P2000.L subset", "Tgetattr/Tsetattr map 1:1 onto the fields OPFS cannot store"); contradicted by include/net/9p/9p.h at tag v2.6.34, https://raw.githubusercontent.com/torvalds/linux/v2.6.34/include/net/9p/9p.h (enum p9_msg_t stops at P9_TWSTAT=126) and fs/9p/v9fs.h L129-137, https://raw.githubusercontent.com/torvalds/linux/v2.6.34/fs/9p/v9fs.h . Kernel version is from research/04-browser-linux-runtimes.md:55 ("The Buildroot image I booted reports kernel 2.6.34.14").

**Failure scenario.** M0 boots Buildroot (kernel 2.6.34.14) and mounts `-o trans=virtio,version=9p2000.L,msize=131072`. The client's message enum in that kernel contains only 100..126 (TVERSION/TAUTH/TATTACH/TFLUSH/TWALK/TOPEN/TCREATE/TREAD/TWRITE/TCLUNK/TREMOVE/TSTAT/TWSTAT) — there is no TLOPEN(12), TGETATTR(24), TSETATTR(26), TREADDIR(40) or TREADLINK(22). So the first `ls /mnt/host` sends Topen(112) and a Tread on a directory fid expecting a stream of marshalled legacy 9P stat structures; the host server, which implements only the .L subset, has no handler and the mount is unusable. Worse for the thesis: symlinks, numeric uid/gid and mknod in 2.6.34 are gated on `v9fs_proto_dotu` (V9FS_PROTO_2000U), a *different* flag from V9FS_PROTO_2000L, so choosing .L turns them all off — `v9fs_vfs_mkspecial` refuses, and stat carries uid/gid as strings with no n_uid. M3's proofs "a symlink the host created reads as a symlink in the guest's ls -l" and "host stat shows mode 0644 with uid equal to the guest process row's credential" cannot pass on this kernel at this version, which is the exact claim the thesis rests on ("the guest's ls -l is only correct because the HOST owns the metadata"). M0's stated mitigation — "read the authoritative message list out of v86's own 9p implementation" — reads the wrong artifact: v86's JS server is a superset; the authority is the guest kernel's client.

**Fix.** Pick the protocol against a chosen kernel, not from memory, and make the kernel choice part of M0: either (a) build/boot a v86 image with Linux >= 2.6.38, where the .L ops (TLOPEN/TGETATTR/TSETATTR/TREADDIR/TREADLINK) actually exist — then the 24-message subset is real; or (b) keep 2.6.34 and implement legacy 9P2000.u instead: Tstat/Twstat with the .u extension (n_uid/n_gid, DMSYMLINK + extension string), Topen/Tcreate, and directory reads as marshalled stat streams. Also drop msize=131072: net/9p/client.c L777-778 clamps msize to `trans_mod->maxsize - P9_IOHDRSZ`, and trans_virtio's maxsize is PAGE_SIZE*16 with P9_IOHDRSZ=24, so the negotiated msize on i386 is 65512, not 131072 — every buffer and short-count rule sized at 131048 is sized against a number the client will never propose.

**Verifier.** SURVIVES. I tried to refute it on four axes and it held on all four; I only shaved the severity.

**1. Mechanism — confirmed, every cited address supports the claim.**
- `enum p9_msg_t` at https://raw.githubusercontent.com/torvalds/linux/v2.6.34/include/net/9p/9p.h ends `P9_TSTAT = 124, P9_RSTAT, P9_TWSTAT = 126, P9_RWSTAT,`. There is no TLOPEN(12), TREADLINK(22), TGETATTR(24), TSETATTR(26) or TREADDIR(40). The docblock above it says so in words: "There are 14 basic operations in 9P2000." The only `.L`-era tokens in the whole header are `P9_DMSYMLINK`/`P9_QTSYMLINK`, both labelled "(9P2000.u)".
- I nearly refuted it here: 2.6.34 *does* accept `version=9p2000.L`. `net/9p/client.c` parses the string (L85-86), sends `Tversion "9P2000.L"` (L682-684) and `p9_is_proto_dotl` exists (L62-66). But that is a trap, and it cuts the critic's way. `fs/9p/v9fs.h` defines `v9fs_proto_dotl()` — and across all of `fs/9p` in v2.6.34 (`vfs_inode.c`, `vfs_super.c`, `vfs_dir.c`, `vfs_file.c`, `vfs_addr.c`, `fid.c`, `v9fs.c`) that inline is called **zero times**. The flag is set at `v9fs.c:273` and never read. So `.L` in 2.6.34 is a negotiable version string attached to no behaviour.
- The "strictly less capable than .u" half is also right, and it is the sharper half. `v9fs.c:273-276` is an `else if`: negotiating `.L` sets `V9FS_PROTO_2000L` and therefore leaves `V9FS_PROTO_2000U` clear. Symlink recognition (`vfs_inode.c:106`, `(mode & P9_DMSYMLINK) && v9fs_proto_dotu`), socket/special nodes (`:108`), numeric uid/gid (`:64`), open-mode translation and `O_APPEND` (`vfs_file.c:64,80`) are all gated on `dotu`. ## 5. Tflush is absent from both the M0 and M3 message sets, but virtio-9p sends Tflush on *every* interrupted request and then waits for Rflush with TIF_SIGPENDING cleared — so Ctrl-C on a parked Tread wedges the guest task permanently instead of returning EINTR.

- Severity: **major** (confidence high)
- Raised against: `hybrid-guest`
- Address: THE DESIGN → milestones[0].deliverable message list and milestones[3] ("the full ~24-message 9P2000.L subset"), plus the `vfs` field's fid table ("Map<u32 fid, {ino, cred, off, iounit, qidvers}>" — no tag map), held against net/9p/client.c at v2.6.34: p9_client_flush L490-515 and p9_client_rpc L577-595, https://raw.githubusercontent.com/torvalds/linux/v2.6.34/net/9p/client.c , and p9_virtio_cancel L184-187, https://raw.githubusercontent.com/torvalds/linux/v2.6.34/net/9p/trans_virtio.c

**Failure scenario.** The control plane parks guestd on `read(/mnt/host/.ctl/req)` and the host deliberately does not reply (the design's core mechanism). The user hits Ctrl-C in that guest terminal, or the host kills a guestexec whose PTY relay is parked on a 9p read. In net/9p/client.c, `wait_event_interruptible` returns -ERESTARTSYS; `c->trans_mod->cancel()` is `p9_virtio_cancel`, which unconditionally `return 1`, so the client calls `p9_client_flush()`, which issues `p9_client_rpc(c, P9_TFLUSH, "w", oldtag)` — and that nested RPC first does `clear_thread_flag(TIF_SIGPENDING)`, so its own `wait_event_interruptible` is no longer signal-interruptible. With no Tflush handler on the host, no Rflush ever arrives: the task hangs forever, the fid is never clunked, and `umount /mnt/host` blocks behind it. That is precisely the pair of assertions M0's proof claims to make — "a Ctrl-C during a second park yields EINTR" and "`umount /mnt/host` after the park succeeds" — so M0 reports a red that looks like the riskiest assumption being false, when the real cause is a missing 5-byte reply. The design also has no tag table to flush against: it defines `Map<u32 fid, {ino, cred, off, iounit, qidvers}>` only, and Tflush is addressed by *tag*, not fid.

**Fix.** Add a tag->parked-request table beside the fid table, implement Tflush as a first-class message (cancel the parked request, then reply Rflush, and never reply to the flushed tag afterwards — per the 9P flush rules, https://9fans.github.io/plan9port/man/man9/flush.html ), and make it an M0 deliverable, not an M3 one. A separate instance of the same class of bug: the fid and tag tables are per-session and are not in the journal or the snapshot, so M6's RESTORE resumes a guest holding fids from a dead kernel instance — every op on /mnt/host then errors and guestd stays parked on a tag no one will ever answer. Either persist the fid/tag tables with the snapshot or force a remount + guestd restart on restore, and assert it.

## 6. Replacing gap-03's unbounded Atomics.wait with a finite TIMEOUT that "retries once then faults the process" makes every legitimately long block a process fault; no fixed TIMEOUT can separate "the kernel is dead" from "the call has not completed yet".

- Severity: **major** (confidence high)
- Raised against: `hybrid-guest`
- Address: THE DESIGN → runtime: "Entry: s=Atomics.load(ctl,SEQ); port.postMessage(callid); Atomics.wait(ctl,SEQ,s,TIMEOUT) ... 'timed-out' retries once then faults the process; Infinity is forbidden", against /Users/chafyni/claude/web-os/docs/research/gap-03.md:42 ("Atomics.wait(c,SEQ,s)", no timeout; "the kernel worker is its only waker") and the blocking calls marked INTR in gap-03.md:25,36 (read, poll, clock_nanosleep, win_poll). Timeout default per https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Atomics/wait is Infinity.

**Failure scenario.** A host process runs `sleep 100` (clock_nanosleep), or the shell sits in `waitpid` while the user edits for ten minutes inside `gexec vim`, or an xterm process sits in `read()` on an idle pty, or any process sits in `win_poll` on a window nobody is touching. The kernel correctly has nothing to reply with, so Atomics.wait returns "timed-out"; the retry parks again and times out again; the process is then faulted into DYING while it was behaving exactly as POSIX requires. M1's own proof runs `sleep 100` and then expects Ctrl-C to return to a prompt — with any TIMEOUT below 50 s that check fails for a reason unrelated to signals, and with a TIMEOUT large enough to cover an idle `read` (hours) the watchdog detects nothing it was added for. gap-03's design has no timeout precisely because it does not need one: the process blocks on exactly one futex word that only the kernel worker ever notifies, so cancellation is by construction, and the design's claim to be "gap-03's ABI verbatim" is false at this line.

**Fix.** Keep the finite timeout only as a re-arm interval and make the loop unbounded: on "timed-out", check a kernel liveness counter that the kernel worker bumps on a timer in the same SAB, and fault only when that counter is stale. That separates a dead kernel from a pending call, and keeps `sleep`, `waitpid`, `read` and `win_poll` blocking indefinitely as POSIX requires. Add a check that a process blocked for 10x TIMEOUT and then satisfied returns the right value rather than a fault.

## 9. OPFS sync access handles are keyed per open-file-description instead of per inode, so the second concurrent open() of any file throws NoModificationAllowedError — an error the 34-call ABI has no errno for.

- Severity: **major** (confidence high)
- Raised against: `minimal-kernel`
- Address: design.vfs: "Every sync access handle lives in OpenFile.handle in the kernel" combined with "Offset lives on the open-file description, not the fd" — the handle is therefore per-description, not per-inode. The project's own research already states the opposite requirement: /Users/chafyni/claude/web-os/docs/research/gap-03.md line 68 — "Two processes opening the same file for writing cannot each hold their own sync handle; the kernel must own the handle and multiplex." Spec: https://fs.spec.whatwg.org/#dom-filesystemfilehandle-createsyncaccesshandle (exclusive lock on the file entry until the handle is closed).

**Failure scenario.** State: notepad (M9) holds fd on /home/user/notes.txt, kernel holds its sync handle in that OpenFile. Input: the shell runs `cat /home/user/notes.txt | wc -l`. cat's open() makes a second createSyncAccessHandle on the same b/<ino> blob file; the fs spec takes the lock on the file entry and the second call rejects with NoModificationAllowedError. Wrong behaviour: open() either throws out of the kernel's syscall handler (the whole kernel worker takes an unhandled rejection mid-dispatch, with 127 other processes parked in Atomics.wait on replies that now never come) or returns an invented errno that no program handles. Same break for `echo a > f` concurrent with `tail f`, and for any two processes sharing a log. POSIX permits both opens, so acceptance criterion 5 ("a real namespace") is false for the ordinary two-process case the thesis is built on ("two programs can be composed without knowing about each other").

**Fix.** Add a kernel-side inode→{handle, refcount} table beneath the OpenFile table: open() creates the handle on the 0→1 transition only, close() closes on 1→0. This also removes the 495 us open cost from every open after the first, and it must land in M3/M6 because the journal's b/<ino> writer needs the same handle. Add an explicit M3 proof: two live processes hold fds on one file, both read and write, and the second open returns a valid fd.

## 12. A process worker is a same-origin dedicated worker, so it holds ambient OPFS access and can read and write the kernel's own backing store directly, bypassing the credential, the mode bits and the syscall channel entirely.

- Severity: **major** (confidence high)  —  **applies to every design**
- Raised against: `minimal-kernel`
- Address: process_model ("Enforcement is the Worker boundary plus the syscall ABI" in threat_model; "A process worker boots a fixed libos.mjs ... then evaluates the program text read from the VFS" in runtime). The research already measured that the storage manager is on WorkerNavigator: /Users/chafyni/claude/web-os/docs/research/gap-06.md line 101 — "persist() is [Exposed=Window] while persisted() and estimate() are exposed on Window and Worker". Sync handles are dedicated-worker-only, which is exactly what a process is: https://developer.mozilla.org/en-US/docs/Web/API/FileSystemFileHandle/createSyncAccessHandle and https://developer.mozilla.org/en-US/docs/Web/API/StorageManager/getDirectory

**Failure scenario.** A uid-1000 program in /usr/bin — say the notepad delivered at M9 — contains `const r = await navigator.storage.getDirectory(); const b = await r.getDirectoryHandle('b'); const h = await (await b.getFileHandle('17')).createSyncAccessHandle(); h.write(new Uint8Array(4096));`. Inode 17 is a root-owned 0600 file. The write lands. The same program reads every file in the system regardless of mode bits, deletes blobs the kernel is not holding open, and `await r.removeEntry('sb.0')` destroys the superblock. M3's credential proof (open("/usr/bin/ls", O_WRONLY) -> -EACCES) still passes, because the credential check is only reached by programs that choose to call the syscall. Acceptance criterion 1 ("an app must be UNABLE to reach the kernel except through the syscall channel") and criterion 5 (mediated namespace) are both false, and no milestone proof in M1-M9 tests ambient capability, so this is discovered only when someone tries it.

**Fix.** libos.mjs must neuter the process realm before evaluating program text: delete the WorkerNavigator.prototype storage getter, and fetch, XMLHttpRequest, importScripts, indexedDB, caches, WebSocket, Worker — then freeze. Add this as M2's third assertion with its own negative control: a probe program must get a TypeError on navigator.storage.getDirectory, and the control is to restore one global and assert the probe FAILS. Without the Worker removal the 128-process cap is also unenforced, and the renderer dies between 3200 and 4800 workers, which kills the whole OS.

**Verifier.** MECHANISM: real, spec-confirmed, not merely cited. I read the IDL in both specs. The FS spec defines `[SecureContext] partial interface StorageManager { Promise<FileSystemDirectoryHandle> getDirectory(); };` (https://fs.spec.whatwg.org/#sandboxed-filesystem) with no `[Exposed]` narrowing, so it inherits `StorageManager`'s `[Exposed=(Window,Worker)]` (https://storage.spec.whatwg.org/#storagemanager); `FileSystemDirectoryHandle` is `[Exposed=(Window,Worker), SecureContext, Serializable]`; `createSyncAccessHandle` is dedicated-worker-only and "takes an exclusive lock on the file entry" (https://fs.spec.whatwg.org/#api-filesystemfilehandle-createsyncaccesshandle). A Narrowgate process is a same-origin dedicated worker sharing the window's storage bucket, so it reaches the same OPFS root the kernel does. The design has no counter-measure: §3.6 (minimal-kernel.md:281) says libos.mjs "installs the 34 sync stubs and then evaluates the program" — no realm lockdown, and `grep -n -i "neuter|delete navigator|WorkerNavigator|freeze(|ambient" designs/*.md` returns nothing in any of the four designs. The finding survives on mechanism.

SCENARIO: follows, with two steps the critic got wrong.
(a) `await r.removeEntry('sb.0')` does not destroy the superblock. §4 (minimal-kernel.md:311) holds the `j.log` and `sb` sync access handles "opened once at boot and never closed", and the design already banks on that exclusive lock as its boot mutex (§4: a second tab's kernel gets `NoModificationAllowedError`). The FS spec leaves removeEntry's exception on a locked entry to the underlying file system (Issue #11 in §2.4.4) but Chrome throws there. Superblock and journal are the one part of the store that is protected — by accident, not by design.
(b) "reads every file in the system regardless of mode bits" overstates the loss. `b/<ino>` holds bytes only; names, tree, mode, uid and nlink live in kernel memory and the locked `j.log`. The attacker gets anonymous blobs keyed by inode, and cannot forge metadata, grant itself uid 0, or plant a root-owned binary. Property 4's namespace mediation (which path resolves to which inode under which cred) is intact; the data layer under it is not. Properties 1-3 (pid, forcible kill, pipe composition) are wholly untouched — nothing here reaches the kernel's process table, fd table, credential or another process's SAB. "Bypassing ... the syscall channel entirely" conflates the persistence substrate with the kernel.

ALREADY HANDLED: disclosed, not mitigated — so "discovered only when someone tries it" is false. research/gap-05.md:56 lists "cross-app storage reads, direct kernel calls" as what only model (ii) per-app-origin rules out, against "nothing hostile" for model (i); research/gap-03.md:102 says "untrusted third-party apps must be a separate tier with no syscall channel at all". minimal-kernel.md:467 adopts the trade verbatim ("Model (ii) buys origin-level storage separation and nothing else"), §8 scopes enforcement to "the worker boundary plus the syscall ABI", and §13:627 declares no untrusted-code tier. The sibling design states the exact mechanism in plain words — fidelity-first.md:749: "A same-origin process worker can open OPFS itself and bypass the VFS entirely... Tier (i) is not confinement of hostile code." So minimal-kernel's real defect is understatement relative to its own research and its sibling, not ignorance.

ADDRESS DEFECT: the quoted acceptance criteria do not exist in the artifact. `grep -rn "UNABLE to reach\|mediated namespace\|criterion 1" /Users/chafyni/claude/web-os` returns zero hits; the only "criteria" in minimal-kernel.md is §12 Kill criteria (line 586). The nearest real text is property 4, minimal-kernel.md:10 — "A program's access to the filesystem is mediated — it can be refused". I judged the finding against that, not against the unverifiable citation.

SEVERITY: fatal downgraded to major. Fatal is the design's own §12 bar — abandon or redesign. This needs neither: ~20 lines in libos.mjs before eval (drop the `navigator.storage` getter, `fetch`, `importScripts`, `indexedDB`, `caches`, `Worker`, then freeze) plus one M2 assertion with the inverted control the critic specifies. The kernel boundary, the ABI, the credential, the 34 calls and every milestone but M2 are unchanged. It stays major rather than minor for two reasons. First, the design's own standard condemns it: CONSTRAINTS.md:164 — "Discipline does not substitute for a boundary" — and property 4 plus Day 14 item 4 ("A refusal") read as boundary claims that M3's `-EACCES` proof cannot support, because that proof only exercises a program that chooses to call the syscall. Second, under the declared first-party model the live failure mode is a buggy program, not a hostile one, and a notepad with a bad path silently corrupting `b/<ino>` behind a journal that never recorded the write is a data-integrity bug the hardening prevents for near-zero cost. The secondary claim about the 128-process cap also holds in part: a nested `new Worker()` is invisible to the process table and counts against the renderer ceiling; per the HTML spec's lifetime rules a nested worker is reaped only when it "stops being actively needed", which is a MAY (https://html.spec.whatwg.org/multipage/workers.html#terminate-a-worker), so teardown after a parent SIGKILL is implementation-timed. §13 already declares an app may "burn CPU and spam the kernel", which covers the spirit of it.

NOT A DISCRIMINATOR: the mechanism is identical in all four designs — every one runs processes as same-origin dedicated workers under threat model (i), and none neuters the realm. The fix and the honesty paragraph belong in all four. Calling it fatal for minimal-kernel alone would mis-rank a design that is, if anything, the one with the least to lose (no WASM tier, no guest, no third-party apps).

NOT MEASURED HERE: I verified by reading spec IDL, not by running a probe in Chrome 157. No browser experiment was run for this review, so the "the write lands" step is spec-derived, not observed. The hardening's own negative control (restore one global, assert the probe fails) is what would close that.

Evidence: https://fs.spec.whatwg.org/#sandboxed-filesystem

## 13. M1, the only milestone that prices the stated riskiest assumption, leaves the offered rate unspecified and asserts nothing about achieved concurrency, so it can report a clean p99 "at N=16" while never putting more than one caller in the kernel queue.

- Severity: **major** (confidence high)
- Raised against: `minimal-kernel`
- Address: milestones[0].proof and kill_criteria[0] ("p99 ... at 16 concurrent processes ... exceeds 5 ms, or mean exceeds 140 us"), against riskiest_assumption ("nothing in the research measures contention"). Confirmed as unmeasured in /Users/chafyni/claude/web-os/docs/research/gap-01.md line 143: "The ~15 us syscall figure is for a kernel whose work is a single await Promise.resolve() ... that number is a channel floor, not a filesystem syscall cost."

**Failure scenario.** The proof says "drive N in {1,4,16,64} processes at a fixed offered rate" and names no rate. Take the design's own numbers: mean kernel service time is 0.98x14us + 0.02x514us = 24us. For the accept bar of mean < 140us, M/M/1 needs utilisation under 0.83, i.e. an aggregate under ~34,600 calls/s, ~2,160 per process — a 3% duty cycle against the 71,000 calls/s a process issues uncontended at 14us. Worse, a harness bug that serialises the drivers (awaiting each process's batch in turn) reports a 15us mean at "N=16" and still passes BOTH stated negative controls — the 20ms stall control proves the harness reads latency, and the no-COOP control proves isolation; neither proves the stimulus was concurrent. That is the webxp contrast-check defect: the control validates the instrument, not the input.

**Fix.** State the rate, and run closed-loop saturation as the primary case with the rate-limited case as secondary. Add a concurrency control: the kernel keeps a max-queue-depth counter and the harness asserts it reached >= N, plus asserts achieved aggregate throughput; the negative control is to serialise the drivers deliberately and assert the depth assertion FAILS. - Severity: **major** (confidence high)
- Raised against: `wasi-userland`
- Address: design `process_model`, "Syscall path, exactly: ... s=Atomics.load(ctrl,SEQ); port.postMessage(callid); Atomics.wait(ctrl,SEQ,s)" (no timeout argument), against `milestones[1].proof`. Directly contradicts /Users/chafyni/claude/web-os/docs/research/gap-01.md:132 — "The kernel MUST answer every syscall, including with an error code, and process-side waits MUST use a finite timeout with a retry loop rather than Infinity. A worker parked on Infinity with a dead kernel is a zombie that terminate() only reaps on the engine's own schedule" — and gap-01.md:103, which notes a reload terminates the owner's dedicated workers (https://html.spec.whatwg.org/multipage/workers.html#terminate-a-worker).

**Failure scenario.** State: 30 processes parked, the shell among them (the shell is itself a wasm process in this design). The kernel worker throws — an uncaught exception on its synchronous OPFS path, a quota error, an OOM. Every parked process is in `Atomics.wait(ctrl,SEQ,s)`, the kernel is SEQ's only notifier, so all 30 stay parked indefinitely; no process is left running to report the fault, the taskbar shows live windows, and `terminate()` only reaps a parked waiter on the engine's own schedule (a waiter was still present 303 ms after terminate and gone by 5000 ms, unbisected). M2's proof terminates the kernel worker at a random journal boundary across 20 seeds, then REBOOTS and asserts filesystem invariants only — and a reload destroys all dedicated workers anyway, so the wedge is structurally unobservable by that check. The defect ships, and the first real sighting is a user whose desktop is alive but totally unresponsive with no error anywhere.

**Fix.** Wait with a finite timeout (e.g. 250 ms) in a retry loop that re-checks a kernel-heartbeat word, returning EIO once the kernel is declared dead. Add the missing check: kill the kernel worker WITHOUT reloading, assert every parked process observes EIO within one grace period, and assert the window manager shows the dead-kernel affordance — with the negative control being a kernel that is alive but slow, which must NOT trip it.

**Verifier.** I tried to refute this on four fronts and it survived three and a half.

1. The wedge is structurally invisible to that check. (c) "totally unresponsive" is overstated: the main thread is not parked, so window drag, resize and the taskbar keep working — which actually sharpens the critic's own point, since the desktop looks healthy while every app is frozen forever.

Confidence high on the omission and the addresses; the residual uncertainty is only the blast radius, which is unmeasured in both the spec and this project.

## 17. Window lifetime is decided entirely by the shell and process lifetime by the kernel, with nothing reconciling them: closing a window cannot be refused, so unsaved work is silently discarded, and after End Process the worker keeps issuing syscalls for ~2 s with no kernel fence.

- Severity: **minor** (confidence medium)
- Raised against: `fidelity-first`
- Address: THE DESIGN, `process_model` ('terminate() ... the table has a DYING state with a 2,500 ms timer and the window is destroyed immediately'), `runtime` win_poll ('EHOSTGONE if the window is gone' is the only event named), and `milestones`[5] proof ('kill the process, assert the pid is gone from /proc'). Windows contract: https://learn.microsoft.com/en-us/windows/win32/winmsg/wm-close — 'An application can prompt the user for confirmation, prior to destroying a window, by processing the WM_CLOSE message and calling the DestroyWindow function only if the user confirms'. Terminate semantics: https://developer.mozilla.org/en-US/docs/Web/API/Worker/terminate.

**Failure scenario.** (a) User types a paragraph in Notepad and clicks the X. The compositor owns every pixel of chrome and the ABI has no close-request event — win_poll's only documented out-of-band result is EHOSTGONE, 'the window is gone' — so the only two codepaths are the app calling win_destroy itself or the shell destroying the frame. The frame is torn down, 'a window with no process is torn down' reaps the process, and the paragraph is gone with no 'Save changes?' prompt. Windows 7 sends WM_CLOSE precisely so the app can refuse. (b) User clicks End Process on a compute-bound app (the design's own dialog routes compute-bound kills to terminate()). The compositor destroys the window immediately — 'the user never sees a dead window' — and the table marks the pid DYING for 2,500 ms. But the measured fact is that the worker runs on for 2004-2051 ms, and the design never says the kernel refuses its syscalls: a process looping write()+fsync() on /home/u/report.txt keeps appending journal records for ~2 s after the UI says it is dead, and keeps calling win_set on a winid the compositor already destroyed (unspecified: only win_poll is documented to return EHOSTGONE). The user relaunches the app inside that window and opens a file that is still being mutated by a process the OS reported as ended. Milestone 5's own proof contradicts the table here: it kills a process and asserts 'the pid is gone from /proc' — either that assertion races the 2,500 ms DYING entry and flakes, or /proc hides a worker that is still executing and the filesystem lies about the process table.

**Fix.** Add a WIN_CLOSE_REQUEST event; the X button posts it and destroys nothing. The compositor destroys the frame only on win_destroy, or after the heartbeat path escalates to the existing Not Responding dialog, so a refused close is a visible 'Save changes?' and not silent data loss. Fence DYING in the kernel: close the pid's fds and release its windows BEFORE calling terminate(), and make every syscall from a DYING pid return an immediate error (-ESRCH) at dispatch, so no write lands after the UI says the app is gone. Keep /proc/<pid> present with state=DYING and change M5's assertion to 'state becomes DYING, then the entry disappears within 2,500 ms' — a check that can distinguish the two.

**Verifier.** The finding is two independent claims welded together. Leg (a), the headline, is refuted. Leg (b) survives as a one-sentence underspecification, not a major defect.

LEG (a) — "closing a window cannot be refused, so unsaved work is silently discarded" — REFUTED on three counts, all in /Users/chafyni/claude/web-os/designs/fidelity-first.md.

## 18. The `guest` driver gives the v86 worker a blocking SAB channel (guest_ctl/win_*) while delivering 9p replies to the same worker by async postMessage — but a worker parked in Atomics.wait cannot service postMessage, so any blocking syscall from the VM worker freezes both the emulator and the entire 9p control plane.

- Severity: **minor** (confidence medium)
- Raised against: `hybrid-guest`
- Address: THE DESIGN → process_model, driver (2) `guest`: "the v86 instance lives in its own dedicated worker; blocking SAB for guest_ctl/win_*, ASYNC postMessage for 9p", against the brief's PROCESSES measurement (parked worker cannot service postMessage) and gap-03's win_poll definition, /Users/chafyni/claude/web-os/docs/research/gap-03.md:36 (`win_poll(winid,timeout)`→event records) and gap-03.md:42 (the process "blocks only on SEQ, and the kernel worker is its only waker").

**Failure scenario.** The framebuffer window has no input path other than the ABI's `win_poll(winid, timeout)`, which blocks the caller in Atomics.wait. The VM worker calls win_poll to collect keyboard/mouse events for the Aero framebuffer window; the user then clicks away onto a host terminal, so no further events are posted to that window. The VM worker is now parked until win_poll's timeout expires. While parked it cannot receive the kernel's async 9p replies, so every guest process blocked on /mnt/host stalls, guestd's SPAWN reply never lands, and the emulator does not advance a single instruction — the VM appears hung, and the control plane that makes guest commands host PIDs is dead for the duration. The same park happens on `guest_ctl(SNAPSHOT)` if the VM worker is the caller: the kernel wants to quiesce in-flight 9p, the in-flight 9p replies cannot be delivered because the caller is parked waiting for guest_ctl to return, and `pending_9p` never reaches zero. The measured fact is explicit: "A worker parked in Atomics.wait CANNOT service postMessage, so it cannot receive a signal or a kill message."

**Fix.** Make the VM worker async-only: it is a driver, not an ABI client. Route guest_ctl and framebuffer input into it as plain postMessage from the kernel, and have the *kernel* answer the blocking guest_ctl syscall of whichever host process issued it. State plainly that the guest row is a process table row whose driver does not use the blocking channel — otherwise the emulator loop and Atomics.wait are competing for the same single thread of execution.

**Verifier.** Tried hard to refute; the mechanism survives, the stated magnitude does not.

STEP 1 — the cited address supports the claim. hybrid-guest.md:261 gives the `guest` row the syscall path "Blocking SAB for `guest_ctl`/`win_*`; **async postMessage for 9p**", and the Proc struct at :240 marks `sab` null only for `guestexec`, so the v86 worker really is an ABI client holding a SAB. gap-03.md:36 defines `win_poll(winid,timeout)` as the only input call in the 71-call table — there is no async input delivery path in the ABI anywhere in either file. gap-03.md:42 confirms the process blocks on SEQ with the kernel as its only waker. The brief's measured fact ("a worker parked in Atomics.wait CANNOT service postMessage") is real and the design itself restates it at :313 — but only to justify SIGPEND-in-SAB for signals, never for the VM worker's own async 9p relay. So the design does put the emulator loop and an Atomics.wait park on one thread, and never says the VM worker must not block. That part is a genuine, design-specific under-specification and nothing in gap-03 or gap-04 resolves it (gap-04 only measures that blocking is faster than async; it says nothing about a worker that must also make autonomous progress).

STEP 2 — the failure scenario needs a step the critic skipped: a long `win_poll` timeout. `win_poll`'s timeout is a caller-chosen argument (gap-03.md:36), and the channel's own park is explicitly finite — hybrid-guest.md:336-342 writes `Atomics.wait(ctl, SEQ, s, TIMEOUT_MS)` and states "`Infinity` is forbidden", with the timed-out branch faulting the process. A VM worker that calls `win_poll(winid, 0)` once per emulation slice parks for one measured round trip (14-16 us), delays queued 9p replies by the same 14-16 us, and the scenario evaporates: no hung VM, no dead control plane. So "freezes both the emulator and the entire 9p control plane", "the emulator does not advance a single instruction", and "the control plane is dead for the duration" are only true under a nonzero-timeout park the design does not mandate. The residual real constraint is narrower: the VM worker may never use `win_poll`'s timeout for what the timeout exists for (avoiding a poll loop), which is a constraint the design should state and does not.

STEP 3 — the SNAPSHOT deadlock does not follow at all, and the critic flags its own missing premise with "if the VM worker is the caller". Nothing in the design makes it the caller: `guest_ctl` takes `a0=vmid` (:372) and the shell-side builtins at :408-410 are host processes; a self-issued `guest_ctl(SNAPSHOT)` on one's own vmid is not a path the design describes. Issued by the shell (a different worker), the quiesce at :567 works: the kernel postMessages in-flight 9p replies, the VM worker is running, `pending_9p` drains. The circular wait is constructed, not found.

STEP 4 — severity. Real but bounded and cheap to close, so not major. Two sentences fix it ("the guest worker polls with timeout 0", or the critic's cleaner version: the kernel pushes framebuffer input into the driver as a plain message). The design's own `guest_ctl(ATTACH_FB)` op (:372) is already a kernel-mediated framebuffer hook, which is evidence the plumbing was headed that way rather than evidence of a committed defect. Downgrade to minor: an unstated load-bearing implementation constraint on one table row, not a broken architecture.

STEP 5 — mostly design-specific, so it is a finding rather than context: hybrid-guest is the only design that admits v86 in v1 as a process row carrying both a blocking SAB and an async 9p channel in the same worker (wasi-userland.md:156 defers v86 off v1; fidelity-first.md:359-371 hands canvas work an OffscreenCanvas). ## 20. The clipboard is a single untyped byte blob and there is no drag-and-drop at all, so the two gestures that make a set of windows feel like one OS cannot be expressed.

- Severity: **minor** (confidence high)  —  **applies to every design**
- Raised against: `hybrid-guest`
- Address: design.runtime (the ABI is gap-03's 68 calls plus three guest calls) against /Users/chafyni/claude/web-os/docs/research/gap-03.md line 36 (clipboard_read/clipboard_write -> bytes/0, gesture-gated, and win_poll -> event records with no drop event) and the browser's own typed-clipboard contract at https://developer.mozilla.org/en-US/docs/Web/API/ClipboardItem ; Win7's delayed-rendering model at https://learn.microsoft.com/en-us/windows/win32/dataxchg/clipboard-operations

**Failure scenario.** The host group's clipboard surface is clipboard_read -> bytes and clipboard_write(bytes) -> 0, with no format argument, no format enumeration, and no delayed rendering (Win7's WM_RENDERFORMAT). Concrete run: a user selects a region in a paint app, presses Ctrl+C, opens a text editor and presses Ctrl+V. The receiving process reads bytes with no way to ask what they are, so it either pastes binary garbage or ignores the paste; there is also no way for the editor to say "I accept text, give me the text flavour of what you copied", which is the behaviour the user expects from Win7. The browser constraint underneath makes the untyped design actively wrong rather than merely thin: ClipboardItem is keyed by MIME type with text/plain, text/html and image/png the mandatory set, so the kernel must carry a type with every blob or it cannot even call the platform API. Separately, both calls are gesture-gated and return ACCES, so a background process, a shell builtin, or any app handling its own Ctrl+C outside a trusted event will fail — and in a terminal window Ctrl+C is consumed by the kernel's line discipline as SIGINT, so the shell's copy path has no gesture to ride at all. Drag-and-drop is worse: dragging notes.txt from an Explorer window onto a terminal window should deliver a path, but win_poll's event records are never enumerated to include a drop, there is no drag-source call, no format negotiation and no drop-effect feedback, and no milestone builds one. Two windows in this OS can exchange data only by one of them knowing the other's filesystem path.

**Fix.** Make the clipboard typed and kernel-owned: clipboard_offer(winid, formats[]) with the kernel keeping a per-format blob (or a promise the owner renders on demand), clipboard_formats() -> list, clipboard_read(format) -> bytes; let the kernel mirror only the three browser-supported MIME types out to the system clipboard and keep every other format internal, so a bitmap or a file list round-trips between two NINEGATE apps even when the host clipboard cannot carry it. Add drag as a first-class win_* verb — win_drag_begin(winid, formats), and DRAG_OVER/DRAG_LEAVE/DROP records in win_poll with a drop-effect reply — and prove it with an Explorer-to-terminal file drop in the same milestone as the taskbar, because this is the check that distinguishes an OS from a website with a taskbar.

## 24. Both of the plan's arithmetic kill gates are evaluated at M1 against a memory-only VFS, so the per-mutation double `flush()` that M2 introduces — ~520 us against a 5 us write, the exact cost gap-04 forbids — is never timed and the "abandon" decision has already been taken green.

- Severity: **minor** (confidence high)
- Raised against: `wasi-userland`
- Address: design `vfs`, "Ordering per mutation: write the blob and flush(), append the journal record and flush()", against `milestones[0].proof` (c) and `kill_criteria[1]`. Contradicts /Users/chafyni/claude/web-os/docs/research/gap-04.md:136 — "fsync MUST be a separate syscall from write. flush() is 260 us against a 5 us 4 KiB write; flushing per write makes the VFS 50x slower for durability nobody asked for" — and leans on gap-01.md:143, which states the 14-16 us round trip "is a channel floor, not a filesystem syscall cost" because the measured kernel's work was one `await Promise.resolve()`. API: https://developer.mozilla.org/en-US/docs/Web/API/FileSystemSyncAccessHandle/flush

**Failure scenario.** M1 has no OPFS persistence (sb.0/sb.1/j.log/b/<ino> are M2 deliverables), so proof (c) `p50 over 20000 fd_write(1,...) under 40 us` measures an in-memory write and passes at ~16 us; kill criterion 2 (abandon above ~60 us) clears on day 12. M2 then mandates "write the blob and flush(), append the journal record and flush()" per mutation. Every 4 KiB append to a growing file is a mutation, so it costs 5 us of data plus two 260 us flushes = ~525 us. Because the kernel worker does OPFS synchronously and there is exactly one kernel, a stock `uu_cat` copying a 2 MB file in 4 KiB writes (512 writes) holds the kernel ~270 ms, during which all other processes' syscalls and every win_*/xterm relay message queue behind it. M2's proof asserts crash consistency and a 50 ms boot only, so it passes. The 100x regression surfaces at M4/M5 as "the terminal feels broken", after every performance gate has reported green, and the headline claim (a syscall-heavy program such as a compiler in a window) is dead on arithmetic nobody re-ran.

**Fix.** Move the write-latency assertion to M2, after the journal lands, measured on a file fd (not fd 1) and stated per 4 KiB append; keep a pipe-path number separately. Flush the journal on fsync, on snapshot (every 512 records) and on a visibilitychange/idle hook — not per mutation — and write the bounded-loss window down as a design fact. Re-state kill criterion 2 against the file path, since that is the path the compiler claim depends on.
